# Naming Glossary — NSE AlgoTrader

Canonical definitions for all identifier terms used across the codebase. When in doubt
about which term to use, use the name from this glossary. Inconsistent naming in order
identity fields is a P0 risk (causes fills, cancels, and rejects to map to wrong orders).

---

## Order Identity Terms

### `client_order_id`

**Definition:** Internal UUID-based order identifier assigned by this system when an
order object is created, before the order is submitted to the broker.

**Format:** `{SYMBOL}_{STRATEGY_ID}_{TIMESTAMP_NS}` or a UUID, encoded compactly enough
to fit in the Shoonya `remarks` field alongside `strategy_id`.

**Source of truth:** Generated by `order_executor.py` at order creation time.

**Where used:**
- `state/live_state.json` — keyed by `client_order_id`
- Broker `remarks` field — encoded as `{client_order_id}|{strategy_id}` [ASSUMED — verify Shoonya field length limit]
- WebSocket order update callback — parsed from `remarks` to recover internal order state
- Audit log — every order event is tagged with `client_order_id`
- Rate limiter — tracks modification count by `client_order_id`

**Do NOT confuse with:** `exchange_order_id` (assigned by broker/exchange, not known until ACK).

---

### `exchange_order_id`

**Definition:** The order number assigned by the broker (Shoonya) or the exchange (NSE)
after a successful order submission. In Shoonya API responses this is `norenordno`.

**Format:** Broker-defined numeric string (e.g., `"24061600001234"`).

**Source of truth:** Populated from broker REST response after order placement, or from
WebSocket order update event.

**Timing:** NOT available when the order is in `NEW` or `SENT` state. Available only after
broker acknowledges (`ACK` state). Storing it immediately on REST response is correct —
this is NOT the ACK, just the broker's assigned number.

**Where used:**
- Required for `cancel_order()` broker call — cancel will fail without this field
- FSM uses this to match WebSocket updates to internal orders when `remarks` is unavailable
- Audit log — stored alongside `client_order_id` for cross-reference

**Do NOT confuse with:** `client_order_id` (our ID, known before submission).

---

### `strategy_id`

**Definition:** SEBI-registered algo strategy tag. This is the identifier that
must appear on every order for regulatory compliance under the SEBI retail algo
circular (Feb 4, 2025). Registered with the broker (Shoonya) at account level.

**Format:** Broker-defined string (e.g., `"NSE-ALGO-001"`). Exact format depends on
Shoonya's registration process.

**Source of truth:** Set via `STRATEGY_ID` environment variable. Required (not optional)
in live mode. Config validator blocks startup if missing in live mode.

**Where used:**
- Broker order payload — all live orders must carry this tag
- Encoded alongside `client_order_id` in the `remarks` field
- `state/config_snapshot_*.json` — logged at startup for audit trail

**Do NOT confuse with:**
- `client_order_id` (per-order identifier)
- `APPROVED_MODEL_VERSION` (model version tag)

---

### `decision_id`

**Definition:** Signal decision correlation ID that traces a single trading decision
from signal generation through order placement, fills, and P&L calculation.

**Format:** UUID generated at signal creation time (e.g., `"d7a3f2c1-8b4e-4d0a-9f21-..."`).

**Purpose:** Enables end-to-end audit tracing. Given a `decision_id`, you can find:
- The feature vector that generated the signal
- The risk check result
- The order(s) created
- All fill events
- The realized P&L attributed to this decision

**Source of truth:** Generated by `signal_hierarchy.py` when a trading decision is
created.

**Where used:**
- Signal log entry
- Order creation (attached to `Order` dataclass)
- Fill events in QuestDB
- P&L attribution in session report
- Audit log

---

### `canonical_id`

**Definition:** Internal instrument identifier used throughout this system, independent
of any broker-specific symbol format. Unambiguous and human-readable.

**Format for equities:** NSE symbol as used in official instruments master, without exchange
suffix (e.g., `"RELIANCE"`, `"TCS"`, `"HDFCBANK"`).

**Format for F&O:** `"{UNDERLYING}-{TYPE}-{STRIKE}-{EXPIRY_YYYYMMDD}"` (e.g.,
`"NIFTY-CE-24500-20260114"`). [ASSUMED — exact format TBD when F&O is implemented]

**Source of truth:** Defined in `config.SYMBOLS` for equities. Derived from instrument
master for F&O.

**Where used:**
- Feature engine — keyed by `canonical_id`
- Position ledger in `LiveSystemState`
- Risk manager — position and correlation checks keyed by `canonical_id`
- QuestDB tables — `symbol` column uses `canonical_id`

**Do NOT confuse with:**
- `tradingsymbol` (broker-specific format, see below)
- `exchange_token` (numeric token used in some WebSocket subscriptions)

---

### `tradingsymbol`

**Definition:** Broker-specific trading symbol format required for Shoonya API calls.
This differs from `canonical_id` and must be resolved via the instrument master.

**Format for equities:** `"{SYMBOL}-EQ"` for most NSE equities (e.g., `"RELIANCE-EQ"`)
but this is NOT reliable for all symbols. Some symbols have different suffixes or series.

**Format for F&O:** Shoonya-specific compact format (e.g., `"NIFTY26114C24500"` for
NIFTY Jan 14 2026 Call 24500). This must NOT be derived by string manipulation —
it must come from the instrument master.

**Source of truth:** Shoonya instrument master file (downloaded via API or from broker
data endpoint).

**Warning:** Do NOT use `f"{symbol}-EQ"` blindly. This fails for indices, ETFs, F&O,
and special series stocks. Always resolve through the instrument master.

**Where used:**
- All Shoonya broker API calls (`place_order`, `cancel_order`, `get_quotes`)
- Shoonya WebSocket subscription

**Do NOT confuse with:** `canonical_id` (our internal ID) or `exchange_token`
(numeric token for WebSocket subscription in some broker APIs).

## Other Key Terms

### `FrozenModelSpec`

A dataclass (`models/model_registry.py`) that locks the exact model version for
production use. Fields include: `version`, `feature_names` (ordered tuple), 
`feature_schema_hash`, `trained_on`, `treelite_so_path`. The hash must match the
feature vector schema at inference time — any mismatch raises `ModelMismatchError`.

### `kill_switch`

A boolean state (represented as a sentinel file `state/kill_switch.sentinel`) that,
when active, halts all new order placement and triggers position flattening. The kill
switch is checked at the start of every order execution attempt. Triggers include:
daily loss limit breach, drawdown limit breach, or manual operator activation.

### ML Class Labels

Fixed mapping — do NOT change:

| Internal class | Trading direction | Meaning |
|---------------|-------------------|---------|
| 0 | Bear / Short | Price expected to fall |
| 1 | Sideways / Hold | No clear directional edge |
| 2 | Bull / Long | Price expected to rise |

The ensemble `predict_proba()` output column order must match: `[P(bear), P(sideways), P(bull)]`.

### Order States (FSM)

| State | Meaning |
|-------|---------|
| `NEW` | Created locally, not yet submitted |
| `SENT` | Submitted to broker, awaiting ACK |
| `ACK` | Broker confirmed receipt (not filled) |
| `PARTIAL` | Partially filled, remainder open |
| `FILLED` | Completely filled (terminal) |
| `CANCELLED` | Cancelled by system or broker (terminal) |
| `REJECTED` | Rejected by broker (terminal) |
| `TIMEOUT` | No ACK within timeout window (terminal, treat as CANCELLED) |

Terminal states: `FILLED`, `CANCELLED`, `REJECTED`, `TIMEOUT`. Rate limiter slot must
be released on any terminal state transition.

### Session Timing Terms

| Term | Default | Meaning |
|------|---------|---------|
| `SESSION_START` | 09:15 IST | NSE continuous trading begins |
| `SESSION_END` | 15:30 IST | NSE continuous trading ends (equity cash) |
| `NO_NEW_TRADES_AFTER` | 15:15 IST | No new entry orders after this time |
| `FORCE_CLOSE` | 15:15 IST | All open intraday positions closed at or before this time |
| `SKIP_FIRST_BAR` | `true` | The 09:15 bar is skipped (opening auction artifacts) |
